# Итоговое решение: роли и доступы платформы «Ясна»

Каркас взят у Варианта 1 (экономика: 0 новых облачных функций, подсадка в `yasna-submit`, вкладка в существующей админке, резолвер в `docs/core/access.js`), но модель данных заменена на вариант 3, потому что ключевое утверждение В1 опровергается кодом (см. ниже), а из В2 забраны только идеи без инфраструктуры вокруг них.

**Одна проверка, которая изменила решение.** В1 предлагал хранить роли и «дефолты роли» строками в `entitlements` под псевдо-владельцами `role:user` / `role:admin`. Так делать нельзя: `server/migrations/002_device_auth.sql:34-36` содержит
`DELETE FROM entitlements WHERE NOT (owner_key LIKE "usr:%" OR owner_key LIKE "dev:%");`
Инвариант «owner_key бывает только `usr:*` или `dev:*`» уже зафиксирован в истории миграций как хозяйственная чистка. Скопировать эти три строки в следующую миграцию — естественный жест того же автора, и он молча снесёт все роли и все дефолты. Поэтому роли — отдельные таблицы, `entitlements` остаётся ровно тем, чем задумана: персональные доступы к контенту по owner_key.

Второе: ручка выдачи прав **пишет** в `entitlements`. Держать там же «кто может выдавать» — значит превратить любую ошибку валидации в самоповышение. Разнесено по разным таблицам + жёсткий серверный отказ на префиксы `role:`, `cap:`, `admin:` в ручке выдачи.

## 1. Сейчас или в конце: частично сейчас

Граница проходит по одному признаку: **зависит ли работа от финального списка разделов**.

**Сейчас (не зависит от разделов, дорожает от ожидания) — этапы 0–6, ~4 дня:**

1. **Открытая ручка записи в живой контент.** Проверено: `server/content-publish.js:125-136` — единственная авторизация это `crypto.timingSafeEqual(provided, process.env.ADMIN_PASSWORD)`; `server/content-publish.js:158` — `publishedBy` берётся из **тела запроса** и лишь обрезается до 80 символов, то есть `content_revisions.published_by` подделывается кем угодно, кто знает один общий пароль. `docs/admin.js:911` монтирует админку сразу, без всякой проверки; пароль спрашивается только в модалке публикации и лежит в `sessionStorage` (`admin.js:411-418`) — то есть постановка «админка закрыта паролем в localStorage» неверна дважды: страница не закрыта вообще, а пароль в sessionStorage. Репозиторий публичный. Это не «нет ролей», это неаутентифицированный редактор и подделываемое авторство. От незафиналенных разделов дверь не станет уже.

Право, выданное гостю, исчезает в момент входа через Telegram. Починить **до** того, как правами начнут пользоваться, иначе позже придётся разбирать «доступ был и пропал».
3. **Последний сантиметр уже проложенной трубы.** `server/progress.js:244` уже читает `entitlements`, `docs/core/storage.js:520` уже кладёт их в `yasna_sync_state_v1`, `:648` уже отдаёт наружу — и **никто не читает** (проверено). Точка вставки клиентского слоя существует буквально: `core/theme.js` и `core/storage.js` подключены строками **7-8** во всех семи страницах и **6-7** в `admin.html`. Стоимость — часы; не сделать сейчас значит написать первый локальный `if`, а потом собирать их по восьми страницам и двум бандлам.

**Потом (прямо зависит от финализации разделов) — этапы 7–8:**

- Гейты внутри `docs/dist/app.min.js` и `docs/dist/duel.min.js`: каждая правка = CI-сборка (node локально не установлен) + дубль в `docs/preview/`. Ключи там ещё будут перетасованы — сделаешь сейчас, переделаешь.
- Права мельче раздела (43 Ясны в `docs/core/data.js:63-116`, темы викторины, банки дриллов, уровни спарринга): ключей десятки, меняются каждый релиз, ценность появляется только с монетизацией.
- Оси полномочий админа («что может делать» × «что может выдавать»), правила Firebase для группы/PvP, серверный прокси к LLM, перенос содержимого за авторизованный эндпоинт.

**Формулировка для владельца:** сейчас ставим замок и ключницу. Решение «какие двери запереть» — это строки в таблицах, оно принимается в конце и меняется без кода и без деплоя. Ровно поэтому «сейчас» безопасно: серверного whitelist фич нет, ключ — свободная строка, новый тренажёр не требует правки бэкенда.

## 2. Модель данных

Один файл `server/migrations/003_access.sql`, **только добавление** (YDB не знает `IF NOT EXISTS`; применение через `scripts/apply-migrations.sh` с `GRPC_DNS_RESOLVER=native`). В `users` не добавляется ни одна колонка — UPSERT при входе (`server/auth-telegram.js:120-132`) не трогаем. Таблица `entitlements` (`001_progress.sql:64-73`) не меняется.

```sql
-- Роли-шаблоны. Роль = набор галочек. Она же «шаблон» для «открыть как у…».
CREATE TABLE roles (
  role_id     Utf8 NOT NULL,        -- 'superadmin' | 'admin' | 'user' | 'teacher' | 'beta'
  title       Utf8 NOT NULL,        -- человекочитаемо, для UI
  rank        Uint32 NOT NULL,      -- 0 user … 90 admin … 100 superadmin
  is_default  Bool NOT NULL,        -- роль для тех, у кого строки нет (ровно одна true)
  updated_at  Timestamp NOT NULL,
  updated_by  Utf8,
  PRIMARY KEY (role_id)
);

-- «У id есть роль». Отсутствие строки = роль с is_default.
CREATE TABLE user_roles (
  user_id     Utf8 NOT NULL,        -- users.user_id (НЕ owner_key: роль только у аккаунта)
  role_id     Utf8 NOT NULL,
  granted_by  Utf8 NOT NULL,        -- 'usr:<id>' | 'bootstrap:ydb-cli'
  granted_at  Timestamp NOT NULL,
  note        Utf8,
  PRIMARY KEY (user_id),
  INDEX user_roles_by_role GLOBAL ON (role_id)   -- нужен для «сколько осталось суперадминов»
);

-- Галочки роли. Это и есть «Админу открыто то, что суперадмин отметил».
CREATE TABLE role_grants (
  role_id     Utf8 NOT NULL,
  feature     Utf8 NOT NULL,        -- 'section:learn' | 'game:partiya:*' | 'cap:content.publish'
  granted     Bool NOT NULL,        -- true открыть / false закрыть
  updated_by  Utf8 NOT NULL,
  updated_at  Timestamp NOT NULL,
  PRIMARY KEY (role_id, feature)
);

-- Каталог возможностей: опубликованный снимок того, что объявляет клиент.
CREATE TABLE features (
  feature        Utf8 NOT NULL,     -- 'section:learn', 'course:stop:novgorod', 'neg:spar:level:hard'
  area           Utf8 NOT NULL,     -- 'constructor'|'course'|'game'|'trainers'|'rating'|'admin'
  parent         Utf8,              -- ключ родителя, для дерева в UI
  title          Utf8 NOT NULL,     -- человекочитаемо
  kind           Utf8 NOT NULL,     -- 'section'|'mode'|'lesson'|'theme'|'widget'|'cap'
  default_access Utf8 NOT NULL,     -- 'open' | 'account' | 'closed'
  status         Utf8 NOT NULL,     -- 'live' | 'wip'  (wip = ещё не готово, только чтение)
  sensitive      Bool NOT NULL,     -- true = закрытие реально проверяется сервером
  declared_at    Utf8,              -- 'docs/learn.html:1263' — откуда узел взялся
  seen_at        Timestamp NOT NULL,
  PRIMARY KEY (feature),
  INDEX features_by_area GLOBAL ON (area)
);

-- Журнал. Append-only: ни UPDATE, ни DELETE. Пишутся и ОТКАЗЫ.
CREATE TABLE access_audit (
  id           Utf8 NOT NULL,       -- uuid
  at           Timestamp NOT NULL,
  actor        Utf8 NOT NULL,       -- 'usr:<id>' | 'bootstrap:ydb-cli' | 'password'
  actor_role   Utf8,
  action       Utf8 NOT NULL,       -- 'role.set'|'role.grants'|'ent.grant'|'ent.revoke'
                                    -- |'features.publish'|'content.publish'|'denied'
  target       Utf8,                -- 'usr:<id>' | 'dev:<id>' | role_id
  feature      Utf8,
  payload_json Utf8,                -- было/стало
  reason       Utf8,                -- обязательно из UI
  ip_hash      Utf8,                -- как в server/submit.js:153
  result       Utf8 NOT NULL,       -- 'ok' | 'forbidden' | 'error'
  PRIMARY KEY (id),
  INDEX audit_by_at     GLOBAL ON (at),
  INDEX audit_by_actor  GLOBAL ON (actor, at),
  INDEX audit_by_target GLOBAL ON (target, at)
);
```

Плюс в том же файле три `UPSERT` в `roles`: `user` (rank 0, is_default true), `admin` (90), `superadmin` (100).

**Почему роль не в JWT.** `server/auth-telegram.js:162-168` кладёт ровно `{sub, nick, iat, exp}`, срок 30 дней, ревокации нет. Роль из токена снималась бы до месяца. Роль читается из БД на каждый запрос — понижение действует мгновенно. Ротация `JWT_SECRET` как «разлогинить всех» невозможна: тот же секрет служит солью для `ip_hash` (`server/submit.js:153`).

**Первый суперадмин.** Войти на сайте через Telegram обычным образом, затем три запроса `ydb` CLI (`GRPC_DNS_RESOLVER=native`), индекс `users_by_tg` уже есть (`server/schema.sql:19`):

1. `SELECT user_id, nickname FROM users VIEW users_by_tg WHERE tg_user_id = <мой tg id>;`
2. `UPSERT INTO user_roles (user_id, role_id, granted_by, granted_at, note) VALUES ("<uuid>", "superadmin", "bootstrap:ydb-cli", CurrentUtcTimestamp(), "первый суперадмин");`
3. `UPSERT INTO access_audit (...) VALUES (..., 'role.set', 'usr:<uuid>', ..., 'ok');` — журнал не должен начинаться с дыры.

Сразу после этого — **второй суперадмин**, из UI. Единственный суперадмин это единственная точка отказа.

Резервный путь, если `ydb` CLI недоступен: одноразовая переменная `BOOTSTRAP_SUPERADMIN_TG` (**одно** значение, без запятой — `scripts/deploy-backend.sh:155-157` аварийно завершает деплой, если в любом значении окружения есть запятая; это же объясняет, почему `EXTRA_GAMES`/`EXTRA_YASNAS` фактически держат одно значение и почему никакие списки id через env невозможны). Срабатывает **только** когда `COUNT(*) FROM user_roles VIEW user_roles_by_role WHERE role_id='superadmin'` равен нулю, пишет журнал, после первого срабатывания мертва. Убрать переменную из окружения явно: `scripts/deploy-backend.sh:150-160` переносит окружение с действующей версии, само оно не исчезнет.

## 3. API

Новую функцию создать нельзя (квота 10/10, разбор в шапке `server/submit.js:80-90`). Подсаживаем в `yasna-submit` тем же приёмом, каким там уже живут `/progress` и `/rooms/*`.

**Разводка (3 правки):**
- `server/submit.js:109` рядом с `isProgressPath` — `function isAccessPath(event){ return /\/access\//.test(reqPath(event)); }`, и в `exports.handler` (`:112-115`) ветка **до всего остального**, через **ленивый** `require('./access.js')` по образцу `progressHandler()` (`:91-93`): синтаксическая ошибка в модуле прав убивает только `/access/*`, а не приём результатов матчей.
- `scripts/deploy-backend.sh:71` — `submit) echo "progress.js rooms-legacy.js access.js" ;;` (одно слово).
- `server/api-gateway.yaml` — пять путей копией блока `/progress` (`:65-112`): `function_id: {SUBMIT_FUNCTION_ID}`, `tag: stable`, у каждого `options` для CORS. Новый placeholder в `scripts/deploy-gateway.sh` не нужен — функция та же.

**Контракты.** Все проверяют роль/полномочие **чтением из БД** на каждый запрос. Отказ → `403 {error:'forbidden', need:'<cap>'}` + строка в `access_audit` с `result='forbidden'` и `ip_hash`. CORS — тот же `ALLOW_ORIGIN`, значит интерфейс обязан жить на том же origin.

| Метод, путь | Тело / параметры | Кто может | Ответ |
|---|---|---|---|
| `GET /access/me` | — | любой с токеном | `{userId, nickname, role:{id,title,rank}, caps:[], catalogSeenAt}` |
| `GET /access/catalog` | ETag | `cap:users.read` или суперадмин | `{features:[…], roles:[…], roleGrants:[…]}` |
| `POST /access/features` | `{nodes:[{feature,area,parent,title,kind,status,sensitive,declaredAt}], reason}` | `cap:features.manage` | `{added, updated, missing:[…]}` — **только upsert**, отсутствующее не удаляется, у него устаревает `seen_at` |
| `GET /access/owners` | `?q=<ник/tg/dev-id>&role=&limit<=100` | `cap:users.read` | `[{ownerKey, userId, nickname, avatar, tgUserId, lastSeenAt, role, grants:N}]` |
| `POST /access/role` | `{userId, roleId, note, reason}` | только `superadmin` | `{ok}` |
| `POST /access/role-grants` | `{roleId, grants:[{feature, granted}], reason}` | только `superadmin` | `{ok, changed:N}` |
| `POST /access/grant` | `{owner:'usr:…'\|'dev:…', grants:[{feature, granted:true\|false\|null, source, expiresAt}], reason}` (≤50 строк, owner ≤160, feature ≤64) | `cap:access.grant` | `{ok, applied:N}`; `granted:null` = DELETE строки («наследовать») |
| `GET /access/audit` | `?limit<=200&actor=&target=` | `cap:audit.read` | `[{at, actor, action, target, feature, reason, result}]` |

**Жёсткие серверные запреты в `POST /access/grant`** (это сердце модели безопасности):
- `feature` с префиксом `role:`, `cap:`, `admin:` или из `area='admin'` → `400`. Полномочия через эту ручку не выдаются в принципе.
- `feature`, которой нет в `features` → `400 unknown feature`. Иначе опечатка `section:trainerz` создаст право-призрак.
- не-суперадмин не может выдать то, что не открыто ему самому.
- нельзя понизить последнего суперадмина (`COUNT` по `user_roles_by_role`) и нельзя понизить себя, если суперадмин один.

**Правки существующих ручек:**
- `GET /progress` (`server/progress.js:227-248`): к `out` добавить `role` и **готовое** `access: {feature: true|false}`, посчитанное сервером, плюс `accessWhy: {feature:'open'|'account'|'closed'|'wip'}` для бейджей. `entitlements` оставить как есть — совместимость. Клиент не складывает политику из кусочков.
- `server/progress.js:356-408` — третий запрос `Q_ENT` (`SELECT feature, granted, source, granted_by, expires_at FROM entitlements WHERE owner_key = $o`) с той же логикой «своё не перетираем»: переносить права с `dev:<device_id>` на `usr:<user_id>`.
- `server/content-publish.js:124-137` — рядом с `ADMIN_PASSWORD` вторая ветка: JWT + `cap:content.publish` из `role_grants`. `publishedBy` (`:158`) брать из `payload.sub`. Пароль оставить рабочим один релиз с `console.warn('deprecated')`, потом убрать переменную из окружения явно; в UI поля пароля больше нет — только «аварийный режим» для curl.
- `scripts/smoke-backend.sh` (после `:60`, формат `check "..." <код> <url>`): `GET /access/me` без токена → 401; `POST /access/grant` с мусорным Bearer → 401; `GET /progress` содержит `"role"`. Обязательно: прод прибит к тегу `stable` (`api-gateway.yaml:11-15`), а откат возвращает прежние версии — непроверенный путь исчезает молча.

**Порядок деплоя жёсткий:** сначала миграция, потом функции. Задеплоенный `access.js` без таблиц отдаёт 500 на каждый запрос прав. Автодеплой бэкенда молчит, пока не задан секрет `YC_SA_KEY` (`.github/workflows/deploy-backend.yml:66-73`), значит вручную: `apply-migrations.sh` → `deploy-backend.sh --promote submit content-publish` → `deploy-gateway.sh` → `smoke-backend.sh`.

## 4. Реестр возможностей: откуда список и почему не гниёт

Правда о том, что вообще можно закрыть, живёт **рядом с самой возможностью**, внутри уже существующих реестров. Одна строка `YasnaAccess.declare({...})` там, где элемент и так объявляется:

**Без сборки (правится и публикуется мгновенно):**
- `docs/core/site-nav.js:10-15` — цикл по `SECTIONS` (экспорт подтверждён: `window.SiteNav = {…, SECTIONS: SECTIONS, …}`, `site-nav.js:69`) → `section:<sec>`.
- `docs/learn.html:1252-1349` — цикл по `STATIONS`; `status` берётся из `action.available` (проверено: `true` только у Москвы, `:1263`), а доступ — отдельно.
- `docs/negotiations/lessons-neg.js:79`, `practice-content.js:9`, `spar.js:39-69` (уровни помечаются `sensitive:true` — в объекте уровня лежит LLM-модель), `contact-content.js:13-134`, `scenarios.js:16`.
- `docs/trainers.html:100,118` и карточки `docs/start.html` — атрибут `data-feature` в разметке (у карточек тренажёров сейчас нет вообще никакого id, это первое, что надо навесить).

**Через CI-сборку, одной пачкой позже:** `docs/games/duel/duel.js:800-810` (declare внутри `YasnaDuels.register` → любой будущий режим попадает в каталог сам), `docs/tours/engine.js:22-46` (то же для гидов), `docs/lessons/lessons-index.js` (цикл по `window.YasnaLessons.lessons`), `docs/app.js:41` (CURRICULUM), `duel-page.js:2171` (modes), `:2142-2146` (темы), `:512-569` (три CTA — declare **на уровне модуля**, не внутри компонента).

**Сборка каталога — в браузере суперадмина, без Playwright, без node, без CI.** Экран «Каталог» открывает восемь страниц в скрытых `<iframe>` того же origin, читает `iframe.contentWindow.YasnaAccess.declared()`, сливает, показывает диф с таблицей `features` и одной кнопкой отправляет `POST /access/features`.

Почему так, а не как в В2: закоммиченный `features.manifest.json` + CI-гейт «харвест против файла» неработоспособен в этом репозитории — `.github/workflows/deploy.yml` ничего не коммитит обратно (собирает и грузит `docs` как Pages-артефакт), а node на машине владельца не установлен, то есть актуальный манифест физически нечем закоммитить; гейт был бы либо вечно красным, либо декоративным. Бонус: манифест не уезжает в публичный репозиторий, и названия ещё не выпущенных разделов не утекают.

**Почему это не потребует правки кода при новом тренажёре.** Новый тренажёр всё равно объявляется в одном из реестров выше (иначе он не появится ни в шапке, ни в каталоге страницы) — значит одна строка `declare`, которая и так несёт заголовок и статус. Дальше: нажать «Собрать каталог» → «Опубликовать». Ни правки прав, ни правки интерфейса суперадмина, ни деплоя бэкенда: на сервере whitelist фич отсутствует, `feature` — свободная строка с проверкой формата `/^[a-z][a-z0-9:._*-]{1,63}$/`. Публикация каталога намеренно ручная: новый раздел не должен молча получать доступ, пока владелец не решил, кому он открыт.

**Маски.** В `feature` допускается суффикс `*` (`game:partiya:*`) — PK `(owner_key, feature)` это позволяет без правки схемы. Резолвер: побеждает самый длинный префикс, при равной длине побеждает `deny`. Ловушка «галочка на `game:*` откроет будущий платный режим» закрывается не флагом, а третьим значением по умолчанию: у платной ветки родительский узел получает `default_access='closed'`, и новые дети ветки закрыты по умолчанию, даже если выше стоит открывающая маска.

## 5. Интерфейс суперадмина

Место: **новая вкладка «Доступы» в `docs/admin.html`**. Там уже React 18 UMD, таб-бар (`docs/admin.js:796-806`, `activeView`) и стили `.ad-*`; страница на том же origin (обязательно из-за одного `ALLOW_ORIGIN`). Плюс поле «вставить токен» для случая «браузер не тот».

Верхняя строка состояния на всех экранах: `Вы: <ник> · Суперадмин` · счётчик суперадминов · кнопка «Аварийный доступ» · «Обновить».

**Подвкладки: Люди · Матрица · Каталог · Журнал · Как увидит.**

### 5.1 Люди
Двухколоночный layout `.ad-grid`.
- Слева: поле поиска (ник / user_id / tg_user_id), фильтр-чипсы `Все / Админы / С исключениями / Гости (dev:)`, список строк: аватар, ник, `usr:12ab…` монофонтом, бейдж роли (цветом), «был 3 дня назад» (`last_seen_at`), счётчик «исключений: N». Под списком отдельное поле «Гостевое устройство» — вставить `dev:<device_id>` и открыть карточку (гость — полноценный сценарий, права живут на owner_key).
- Справа — карточка владельца, четыре блока:
  1. **Роль**: радиогруппа `Пользователь / Админ / Суперадмин` + срок «до» (дата, пусто = бессрочно). Понижение последнего суперадмина блокирует Save с подписью «останется 0 суперадминов». Для `dev:*` блок скрыт (роль только у аккаунта).
  2. **Полномочия** (виден только для роли Админ; у суперадмина всё отмечено и залочено): шесть чекбоксов человеческими словами — Публиковать контент · Выдавать доступы · Видеть людей · Видеть журнал · Править каталог · Управлять ролями. Пишутся как `cap:*` в `role_grants` роли, не в `entitlements`.
  3. **Доступы**: дерево каталога (только узлы, где эффективное право отличается от роли, плюс кнопка «показать всё»); в строке трёхпозиционный переключатель `наследовать · открыть · закрыть` = ровно семантика таблицы (нет строки / `granted=true` / `granted=false`), рядом `source` (`manual/promo/teacher/purchase`) и «до». Явное «закрыто» отличается цветом от «закрыто по умолчанию» — это разные состояния.
  4. **Шаблоны**: две кнопки. «Открыть как у…» → picker человека → предпросмотр дифа («+4 открыть, −1 закрыть») → применить одним `POST /access/grant` с автоподставленной причиной «как у <ник>». «Назначить роль-шаблон» → выбор роли из `roles` (кастомные роли `teacher`/`beta` создаются на экране Матрица).
  Внизу — обязательное поле **«Причина»** (без него Save заблокирован) и хвост журнала по этому владельцу (5 строк).

### 5.2 Матрица прав — главный экран
Ни одного названия раздела в коде страницы: дерево строится из `GET /access/catalog` по `parent`.
- Шапка таблицы (sticky): `Возможность` · `Статус` · `По умолчанию` · `Гость` · `Пользователь` · `Админ` · `Суперадмин` · `Выдано вручную`.
- Строки — узлы с отступом по уровню: Разделы → Игра → Партия → соло/pvp/группа, длительности, темы; Тренажёры → Переговоры → спарринг → 3 уровня, 10 банков, 7 встреч; Курс → 8 остановок; Конструктор → 3D, астро, оверлей, редактор, 6 гидов, уроки.
- `Статус`: `live` / серый бейдж `Скоро` (только чтение, приходит из продукта).
- `По умолчанию`: радио из трёх — `открыто` / `нужен вход` / `закрыто`.
- Колонки ролей: трёхпозиционные ячейки `✓ / ✗ / —`. Клик по строке-родителю пишет **маску** (`game:partiya:*`), а не 30 ключей; в тултипе прямым текстом «включая будущие пункты этой ветки». Колонка Суперадмин всегда `✓` и залочена. Колонка Гость = роль `user` + признак «без входа» (различает `account`).
- Бейджи в строке: `новое` (появилось после последней публикации каталога), `Скоро` (галочки нет вовсе — открыть ненаписанное невозможно по конструкции), `сирота` (право выдано, ключа в каталоге больше нет), `серверное` (`sensitive:true` — закрытие реально работает) против `витрина` (гейт снимается в DevTools).
- `Выдано вручную: N` — ссылка на отфильтрованный экран Люди.
- Фильтры сверху: поиск по названию, `только закрытые`, `только отличается от дефолта`, `только серверные`.
- Кнопка «+ Роль» — создать роль-шаблон (`role_id`, `title`, `rank`).
- Каждый щелчок — один `POST /access/role-grants`, оптимистичное обновление, при ошибке красная плашка и откат значения.

### 5.3 Каталог
Три списка и одна кнопка. `Собрать каталог` (скрытые iframe восьми страниц, прогресс-бар «3 из 8») → диф: **появилось в приложении** (нет в БД), **пропало из приложения** (есть в БД, `seen_at` устарел — не удаляем, показываем плашкой), **расхождение названий/статусов**. В каждой строке тихая ссылка `declared_at` (`docs/learn.html:1263`) — видно, откуда узел взялся. Кнопка `Опубликовать каталог` → `POST /access/features`. Отдельным блоком — **права-сироты**: право висит в воздухе, ключа нет; подсвечивать громко, а не как деталь.

### 5.4 Журнал
Таблица из `GET /access/audit`: `когда · кто · роль · действие · над кем · возможность · причина · результат`. Строки с `result='forbidden'` — красным (по ним видно, что кто-то перебирает права). Фильтры по актору и цели, `limit` 200, выгрузка CSV. Только чтение.

### 5.5 Как увидит
Селектор `роль | конкретный владелец`. Страница пересчитывает `can()` **тем же самым** `docs/core/access.js` по правилам выбранного и показывает две колонки — «открыто» и «закрыто», сгруппированные по областям, с указанием причины (`роль`, `исключение`, `по умолчанию`, `Скоро`). Никакой подмены запросов и входа под чужим id. Это дешёвая страховка от единственной ошибки, которая для одного человека реально страшна: закрыл лишнее и не заметил.

## 6. Что видит пользователь у закрытого раздела

Три состояния, которые нельзя путать (в коде уже живут четыре независимых механизма «ещё не готово»: `learn.html` `available:false` у 7 из 8 станций, `app.js` `status:'planned'`, «Расклад» `disabled` — `duel-page.js:573`, «Тема дня» `ready:false` — `:619`).

1. **«Скоро»** (`status='wip'`) — существующий вид: серая карточка, надпись «Скоро». Ничего не меняется, галочки в матрице нет, право не может это «включить».
2. **«Нужен вход»** (`default_access='account'`) — карточка на месте, бейдж `✦ После входа`, подпись «Войдите через Telegram — прогресс сохранится на любом устройстве», кнопка ведёт в `duel.html#login`. Самое понятное человеку состояние и, скорее всего, 80% реальных потребностей на год.
3. **«По доступу»** (`closed`) — карточка **остаётся на месте**, приглушена (`opacity .55`, замок в углу), бейдж `По доступу`, под ней строка из `lockedHint`: «Открывается по доступу — напишите @YasnaDuelBot». Клик ведёт в объяснение, не в тупик. Исчезновение раздела читается как поломка сайта и убивает будущий апсейл: нечего показать — нечего продать.

**Скрывать совсем** — только `area='admin'`: пункт не появляется в шапке (`site-nav.js`) и на лендинге.

**Прямой URL** перехватывает `Access.gate(feature)`: содержимое страницы заменяется тем же блоком «По доступу» с кнопкой «Войти» и ссылкой «Вернуться» — не 404, не белый экран, не редирект в никуда. Вход по query-параметру гейтится отдельно (`docs/app.js:862-877`, `?lesson=N` и `?lessons=1`), иначе карточка обходится ссылкой.

**Истёкший `expires_at`** ведёт себя как отсутствие строки (возврат к правилам роли), а не как запрет.

**Порядок разрешения** (считает сервер, отдаёт готовым в `access`; клиент повторяет тот же порядок только для отрисовки):
`status='wip'` → закрыто · роль `superadmin` → открыто · строка `entitlements` владельца (длиннейший префикс, `deny` при равенстве, с проверкой срока) · `role_grants` роли · `features.default_access` (`account` = открыто при наличии токена) · нет узла → открыто, кроме `admin:*`/`section:admin` → закрыто.

**По умолчанию открыто (fail-open).** Так уже описана таблица в комментарии миграции (`001_progress.sql:61-63`: «Отсутствие строки = доступ по общим правилам»), и так безопаснее: гость без входа — полноценный сценарий, платформа бесплатная, а fail-closed означает, что любой раздел, добавленный до публикации каталога, исчезнет у всех, включая владельца. Исключение — `area='admin'` и узлы `sensitive:true`.

## 8. Что этот план НЕ решает

1. **Клиентский гейт — витрина, не защита.** `docs/` раздаётся статикой с публичных Pages: `docs/lessons/*.js`, `docs/negotiations/*.js`, `content.bundle.js`, `dist/*.min.js` качаются по прямому URL, `GET /content` полностью публичен, кнопка возвращается через DevTools. Реально проверяются сервером только: публикация контента, все `/access/*`, роль в `/progress`. **Продавать можно только узлы с `sensitive:true`** — это правило надо записать комментарием в `core/access.js`, а не держать в голове.
2. **Живой спарринг не гейтится в принципе.** `docs/negotiations/spar.js:99` берёт ключ из localStorage и ходит в LLM напрямую. Любая монетизация обходится своим ключом, пока нет серверного прокси — а прокси это ещё одна ручка на `yasna-submit` плюс контроль расходов.
3. **Группа и PvP — второй, неподчинённый контур.** `firebase-rules.json` публикуется вручную через консоль и проверяет только `auth != null`; `signInAnonymously` (`rt-firebase.js:52-65`) не связан с `user_id`. Право «С коллективом» остаётся косметическим: «кнопка закрыта, комната открыта».
4. **`docs/preview/*` — полная вторая живая копия сайта** на том же Pages (`admin.html`, `admin.js`, `app.js`, `core/`, `games/`, `lessons/`, `negotiations/`, `dist/`, 9 HTML). Каждый гейт ставится дважды, иначе preview — обход в один URL. Дешевле навсегда: вывести preview из публикуемой директории; это отдельное решение, план его не принимает.
5. **Мгновенность только на сервере.** Роль читается из БД → отзыв действует сразу для серверных проверок. Но клиентский `access` живёт в `yasna_sync_state_v1` до следующего pull (синк стартует через ~1.2 с после загрузки) — «отключил, и сразу закрылось» в чужом браузере обещать нельзя.
6. **Гость = устройство, а не человек.** Чистка localStorage даёт новый `device_id` и новый секрет; выданное на `dev:*` право теряется вместе с прогрессом. Ничего платного на гостевое устройство вешать нельзя.
7. **Версионности правил нет.** Журнал append-only с `before/after` в `payload_json` — это восстановление вручную, а не кнопка «откатить правку правил». `UPSERT` в `entitlements`/`role_grants` перезатирает состояние.
8. **Оси полномочий админа урезаны.** Есть роль + `cap:*` в `role_grants`; нет «что именно этот админ может выдавать» (области). Пока админ один, это не нужно; добавляется позже без миграции — теми же строками в `role_grants`.
9. **Нет платёжки.** `source='purchase'` предусмотрен схемой, но никто его не пишет. При появлении онлайн-оплаты центр тяжести уезжает на серверную выдачу контента, и `section:*` окажется слишком грубым.
10. **Отзыв JWT невозможен.** Токен 30 дней; ротация `JWT_SECRET` обесценит ещё и `ip_hash` (`submit.js:153`). Именно поэтому в токене остаётся только личность.
11. **Каталог видит только то, что объявлено при загрузке страницы.** `declare` внутри React-компонента, монтируемого по клику (пикер длительностей, лобби), в каталог не попадёт, и это не поймает ни один автоматический тест. Правило «declare только на уровне модуля» — дисциплина, а не гарантия.
12. **Тулчейн хрупкий.** Миграции только вручную (`YC_SA_KEY` не задан), `ydb` CLI требует `GRPC_DNS_RESOLVER=native`, bash 3.2, node локально нет → любые бандлы только через CI. И жёсткое ограничение: **никаких значений с запятой в окружении функций** — `scripts/deploy-backend.sh:155-157` аварийно завершает деплой, включая путь выкатки исправления.
