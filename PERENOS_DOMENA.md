# Переезд yasnalab.ru на Яндекс Object Storage

Тем же путём, каким 19.08.2026 переехал `zolotoj-yasen.ru`: статика в Object
Storage, перед ней CDN Яндекса, сертификат Let's Encrypt через Certificate
Manager, DNS в Яндекс Облаке. Причина та же — GitHub Pages фильтруется из
московских сетей.

Отдельно: **сайт закрыт от поисковиков в три слоя.** Подробности в конце.

---

## Почему переезд вообще нужен

`yasnalab.ru` сегодня не работает. DNS настроен верно — все четыре A-записи
GitHub Pages и поддомен `www`, — но Pages этот домен не знает:

```
Host: yasnalab.ru → 404 от Pages
SSL: no alternative certificate subject name matches target host name 'yasnalab.ru'
```

Сертификат для домена никогда не выпускался, потому что домен не привязан в
настройках Pages репозитория. Одного файла `docs/CNAME` для этого не хватило.

Можно было бы просто добить привязку на Pages — но тогда домен остался бы на
инфраструктуре, которая у московской аудитории уже отваливалась.

---

## Что уже сделано в облаке

Всё, что можно было сделать без доступа к личному кабинету регистратора.

| Что | Идентификатор | Состояние |
|-----|---------------|-----------|
| Бакет `yasnalab.ru` | — | сайт залит, 108 объектов, 7,7 МБ, хостинг включён |
| Группа источников | `7675229783702382295` (`yasnalab-bucket`) | → `yasnalab.ru.website.yandexcloud.net` |
| Ресурс CDN | `bc8rmtp2lqnn7dhc2myx` | активен, `X-Robots-Tag: none`, кэш 120 с / 60 с |
| Зона DNS | `yasnalab` → `yasnalab.ru.` | повторяет нынешние записи reg.ru |
| Сертификат | `yasnalab-site` (`fpqhlur9u6pncg7qm00c`) | `VALIDATING` — ждёт делегирования |

Сайт из хранилища уже отдаётся правильно — проверено:

```
/                → 200  text/html; charset=utf-8
/robots.txt      → 200  text/plain; charset=utf-8
/duel.html       → 200  text/html; charset=utf-8
/нет-такой-стр.  → 404  (страница 404.html)
```

Типы файлов проставлены явно. Это не мелочь: Object Storage сам их не ставит,
`.css` уезжает как `text/plain`, и браузер такие стили просто не применяет —
сайт открывается голым текстом.

**Зона DNS создана нарочно как точная копия нынешней.** В ней стоят те же
адреса GitHub Pages, что сейчас у reg.ru. Значит смену серверов имён можно
сделать в спокойный момент и без простоя: сайт продолжит открываться там же,
где открывается сегодня. Переключение на CDN — отдельный последний шаг.

---

## Что должны сделать вы

### 1. Делегировать домен Яндексу — у регистратора

В личном кабинете reg.ru для `yasnalab.ru` заменить серверы имён на:

```
ns1.yandexcloud.net
ns2.yandexcloud.net
```

Расходится это от получаса до суток. Пока идёт — сайт работает по-старому,
потому что записи в зоне те же.

Как только делегирование дойдёт, сертификат `yasnalab-site` выпустится сам:
записи подтверждения `_acme-challenge` уже лежат в зоне.

### 2. Завести ключ для выкладки — в терминале

```bash
./scripts/set-storage-key.sh
```

Скрипт создаст ключ служебному аккаунту `yasna-deploy` (единственная роль —
`storage.editor`) и покажет пару значений. Перенесите их в
[секреты репозитория](https://github.com/Avvacumrechevoi/yasnanegotiations/settings/secrets/actions):

```
YC_S3_KEY_ID
YC_S3_SECRET
```

Секретная часть показывается один раз и нигде больше — поэтому отдельный скрипт,
а не переписка.

Пока секретов нет, шаг выкладки в хранилище пропускается сам, и публикация на
Pages идёт как раньше. Сломать этим ничего нельзя.

### 3. Влить ветку `perenos/hranilishche`

В ней одна правка `.github/workflows/deploy.yml`: выкладка теперь идёт **в оба
места** — в хранилище (боевое) и на Pages (запасная площадка, куда домен
возвращается одной правкой DNS).

Заодно на прод перестаёт уезжать служебное: раньше публиковался `docs/` целиком,
вместе с `.DS_Store` и четырьмя `README.md`. Это та же дыра, что нашлась в
yasna3 11.08.2026, когда на боевом домене открытым текстом лежали материалы
запуска.

## Последний шаг: переключить домен на CDN

Делать **только после** того, как сертификат перешёл в `ISSUED`, и **только по
проверке снаружи**. Порядок ровно тот, что сработал на yasna3.

```bash
export PATH="$HOME/yandex-cloud/bin:$PATH"

# 0. Сертификат выпущен?
yc certificate-manager certificate get --name yasnalab-site --format json \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["status"])'

# 1. Привязать сертификат к CDN и включить переход на https
yc cdn resource update bc8rmtp2lqnn7dhc2myx \
  --cert-manager-ssl-cert-id fpqhlur9u6pncg7qm00c \
  --redirect-http-to-https

# 2. Сначала ТОЛЬКО www — как пробная площадка
yc dns zone replace-records --name yasnalab \
  --record "www 300 CNAME bdd676f8d5e77253.topology.gslb.yccdn.ru."

# 3. Проверить www СНАРУЖИ (check-host.net → check-http).
#    Ждать, пока станет 35+ узлов из 40. Сертификат расходится по узлам
#    десятками минут: сразу после привязки будет «Connection reset by peer»
#    на большинстве. На yasna3 разошлось за ~40 минут: 12/40 → 29/40 → 39/40.

# 4. И только теперь корень
yc dns zone replace-records --name yasnalab \
  --record "@ 300 ANAME bdd676f8d5e77253.topology.gslb.yccdn.ru."
```

**Три грабли, на которые я уже наступал на yasna3:**

1. **Проверять CDN из терминала этой машины нельзя.** Песочница ходит через
   прокси, который разрешает имя сам и игнорирует `--resolve` и подмену `Host`.
   Проверка «CDN отдаёт 200» на деле мерила GitHub, и отличить было невозможно:
   сертификат у обоих от Let's Encrypt на то же имя. Мерить только снаружи —
   check-host.net.
2. **Сертификат расходится по узлам десятками минут.** Переключать корень
   только после подтверждения снаружи.
3. **Корень без пробной площадки — плохая идея.** Один раз переключил сразу и
   уронил сайт до 5 узлов из 40. Откат по TTL 300 занял полминуты, но лучше не
   доводить.

### Мина, которая сработает ровно в момент переключения

Как только `yasnalab.ru` начнёт отвечать, **блок профиля игрока умрёт с 403**.

`/profile` — единственный эндпоинт с настоящей проверкой Origin, и в его белом
списке только старый адрес. Проверено:

```
Origin: https://avvacumrechevoi.github.io  →  200
Origin: https://yasnalab.ru                →  403 {"error":"origin not allowed"}
```

Чинить придётся не правкой: **исходника функции `yasna-profile` в репозитории
нет**, она живёт только в облаке (`server/README.md:25` это признаёт). Значит
либо переписывать заново, либо снимать проверку через переменную окружения —
но у `yasna-profile`, в отличие от остальных функций, переменной `ALLOW_ORIGIN`
не задано вовсе, то есть список зашит внутри утраченного кода.

Это надо решить **до** шага 4, а не после. Всё остальное на новом домене
работает: у остальных 25 путей проверки Origin нет вовсе — заголовок только
проставляется в ответ.

Заодно перестанет работать вход через Telegram, пока в BotFather не заменён
домен виджета.

## Как сайт закрыт от поисковиков

Три слоя, каждый закрывает то, чего не закрывают другие.

**1. `robots.txt` — запрещает обход.** Уже был:

```
User-agent: *
Disallow: /
```

Отдельно перечислены Yandex и Googlebot.

**2. `<meta name="robots" content="noindex, nofollow">` — запрещает показ в
выдаче.** Проверено: стоит на всех одиннадцати страницах, включая `404.html`,
`games/krug/index.html` и `games/duel/v2/duel.html`.

**3. `X-Robots-Tag: none` — заголовок от CDN. Это новое.** Он приходит с
**каждым** ответом, а не только со страницами: с `.json` банка вопросов, с
бандлами, с картинками. Мета-тег внутрь JSON не положишь, а заголовок работает
везде. `none` — это ровно `noindex, nofollow` одним словом; понимают и Google, и
Яндекс.

Проверить после переключения:

```bash
curl -sI https://yasnalab.ru/ | grep -i x-robots-tag
curl -sI https://yasnalab.ru/games/duel/content.bundle.js | grep -i x-robots-tag
```

### Чего это не закрывает

Заголовки и `robots.txt` — просьба к поисковику, а не замок. Содержимое
по-прежнему качается по прямой ссылке любым, кто знает адрес: банк вопросов с
правильными ответами, уроки, код админки. Пароль `core/gate.js` прячет только
вид страниц — он сам это признаёт в комментарии («это занавеска на время
стройки, а не защита»).

Если доступ нужно закрыть по-настоящему, а не спрятать от поиска, — это другая
работа: контент должен отдавать сервер по токену, а не хранилище всем подряд.
